# ReceiptPilot 要件定義書(v2)

AI-OCR レシート → 家計簿/仕訳 自動化パイプライン

- 作成日: 2026-07-19
- 対象フェーズ: B2C(iPhone家計簿版)。B2B(税理士事務所向け)はアダプタ差し替えで対応
- 前提: Mac(処理側)+ iPhone(撮影側)、Anthropic API、実物レシートで運用しながら育てる

---

## 0. 背景と戦略

- ダミー証憑では感熱紙のかすれ・折れ・レシート特有の変な店名表記が再現できない。
  **自分の実物レシートで先にコアを鍛え、後からB2B版へ移植する**。
- コア(抽出/ルール/判定/学習/保存)はB2C/B2B共通。**違いは出力アダプタだけ**。

## 1. 設計原則(3本柱)

1. **迷ったら安全側へ倒す** — 確信が持てないレコードは自動確定せず「要確認」に落とす。
   誤った自動確定1件は、要確認100件より害が大きい。
2. **自分ルールがAIの推測に勝つ** — payee_rules に登録された対応付けは、
   AIの推測より常に優先される。ユーザーの決定が最上位。
3. **コアは共通、違いはアダプタだけ** — 家計簿CSV / GASシート / freee の差は
   出力アダプタ内に閉じ込める。コアロジックに分岐を持ち込まない。

## 2. スコープ

### やること (In)
- iPhoneで撮影したレシート画像の取り込み(iCloud/AirDrop/ショートカット経由)
- VLM(Claude API)による構造化抽出(店名・日付・合計・税・明細・支払方法)
- 自分ルール(payee_rules)による費目の決定
- 信頼度判定による「自動確定 / 要確認」の振り分け
- Streamlit UI での要確認レコードの人手確認・修正
- 確定結果からのルール候補学習(learn)
- 出力アダプタ: 家計簿CSV / Googleスプレッドシート(GAS) / freee取込CSV

### やらないこと (Out)
- レシート画像の前処理(傾き補正・二値化) — VLMに直接投げる。品質不足なら再撮影を促す
- 完全自動運転 — 要確認ゼロ化は目標にしない(原則1に反する)
- クラウドサーバ常駐 — ローカル(Mac)実行のみ。プライバシーとコストの観点

## 3. 機能要件

### FR-1 取り込み
- `data/inbox/` に置かれた画像(jpg/png/heic→jpg変換済)を未処理分だけ処理する
- 同一画像の二重処理を防止(ファイルハッシュで管理)

### FR-2 抽出 (extract)
- Claude API の tool 定義で型を強制した構造化抽出(自由文パースはしない)
- 抽出項目: 店名(raw)、日付、合計、税額、明細(品名/金額)、支払方法、通貨
- モデルは設定で切替(既定: claude-sonnet-4-6 / 低コスト: claude-haiku-4-5)
- **検算**: 明細合計と合計金額の突合。不一致は confidence を下げる
- オフラインテスト用に MockExtractor を同梱(APIキー不要でパイプライン検証可能)

### FR-3 店名正規化(ブランド抽出)
- 「区切り(スペース・記号)があるときだけ」支店名を落とす
- 区切りが無い・曖昧な場合は raw のまま保持し、人に決めさせる
  (自動での無理な分割は原理的に曖昧 → 原則1に従い安全側)

### FR-4 自分ルール (rules)
- payee_rules.yaml: 店名パターン → 費目・ブランド名の対応
- マッチ方式: 完全一致 > 前方一致 > 部分一致 の優先順
- ルール由来の費目は AI 推測を常に上書きする(原則2)

### FR-5 信頼度判定 (judge) — 「ルールが信用を獲得する」
一律しきい値は機能しない(前回実測)。金額×ルール既知性の二軸で判定する:

| 条件 | 自動確定の条件 |
|---|---|
| 30,000円超 | 常に要確認(金額の絶対防衛線) |
| 自分ルールに載っている店 | 20,000円以下なら自動確定可 |
| ルールに無い店(AI推測のみ) | 3,000円以下なら自動確定可 |
| 検算不一致・必須項目欠落 | 常に要確認 |

想定例: よく行く店のルールを1つ足すと、その店のレシートは以後すべて自動確定に回る(実レシートでの実測は M1 で記録する)

### FR-6 学習 (learn)
- 人手確定した (店名, 費目) ペアからルール候補を生成
- 同じ対応付けが2回確定されたら payee_rules への追加を提案(自動追加はしない)

### FR-7 出力アダプタ
- FR-7.1 共通IF: `validate(record) -> list[str]` / `emit(records) -> path`
- FR-7.2 **最終検証ゲート(全アダプタ必須)**: 項目充足に加えて
  `status == "confirmed"` を必ず検査する。未確定レコードは全項目が
  埋まっていても書き出さない(前回、status未検査バグで事故りかけた教訓)
- kakeibo_csv: 日付/店名/費目/金額 のUTF-8 CSV
- gas_sheet: GAS Webhook へ POST する形式のJSON(またはCSV)
- freee: freee「取引インポート」形式CSV

### FR-8 確認UI (Streamlit)
- 要確認レコード一覧 → 画像プレビュー + 抽出結果の並列表示 → 修正 → 確定
- 確定時に learn へルール候補を送る
- 統計表示: 自動確定率、要確認件数、費目別集計

### FR-9 保存 (store)
- JSONL 追記型ストア(`data/store/records.jsonl`)。DB不要
- 全レコードに status(confirmed / review / manual)、来歴(extractor/rule/human)を持つ

## 4. 非機能要件

- **プライバシー**: 画像・データはローカル保持。API送信は抽出時の画像のみ。
  B2B展開時は個人情報保護法対応(利用目的明示・保管期間)を要件化
- **コスト**: 1枚あたり数円以下(sonnet)。月100枚で誤差レベル
- **可搬性**: Python 3.11+、依存は anthropic / streamlit / pyyaml のみ
- **再開性**: HANDOFF.md に環境構築〜運用開始の手順を常に最新化

## 5. 受け入れ基準

1. MockExtractor でパイプライン全段(取込→抽出→ルール→判定→保存→出力)がテスト通過
2. 実APIで実物レシート10枚を処理し、要確認振り分けが原則1に沿うこと
3. 未確定レコードがどのアダプタからも出力されないこと(FR-7.2)
4. ルール追加前後で自動確定率が向上することを統計で確認できること

## 6. マイルストーン

- M0: コア実装 + Mockテスト通過(完了)
- M1: Mac実機セットアップ、実APIで実物レシート10枚
- M2: iPhoneショートカット連携、1週間の実運用
- M3: デモ動画撮影 + note記事公開
- M4: B2B版(freeeアダプタ本番検証、税理士事務所向け要件追加)
