# ReceiptPilot 要件定義書(v2.2)

AI-OCR レシート → 家計簿/仕訳 自動化パイプライン

- 作成日: 2026-07-19 / 更新日: 2026-10-20(実装と実物レシートの検証結果に合わせて改訂。変更点は末尾の「改訂履歴」)
- 対象フェーズ: B2C(iPhone家計簿版)。B2B(税理士事務所向け)はアダプタ差し替えで対応
- 前提: Mac(処理側)+ iPhone(撮影側)、Anthropic API、実物レシートで運用しながら育てる

---

## 0. 背景と戦略

- ダミー証憑では感熱紙のかすれ・折れ・レシート特有の変な店名表記が再現できない。
  **自分の実物レシートで先にコアを鍛え、後からB2B版へ移植する**。
- コア(抽出/ルール/判定/学習/保存)はB2C/B2B共通。**違いは出力アダプタだけ**。

## 1. 設計原則(3本柱)

1. **迷ったら安全側へ倒す** — 確信が持てないレコードは自動確定せず「要確認」に落とす。
   誤った自動確定1件は、要確認100件より害が大きい。
2. **自分ルールがAIの推測に勝つ** — payee_rules に登録された対応付けは、
   AIの推測より常に優先される。ユーザーの決定が最上位。
3. **コアは共通、違いはアダプタだけ** — 家計簿CSV / GASシート / freee の差は
   出力アダプタ内に閉じ込める。コアロジックに分岐を持ち込まない。

## 2. スコープ

### やること (In)
- iPhoneで撮影したレシート画像の取り込み(iCloud/AirDrop/ショートカット経由)
- VLM(Claude API)による構造化抽出(店名・日付・合計・税・明細・支払方法)
- 自分ルール(payee_rules)による費目の決定
- 金額とルール既知性による「自動確定 / 要確認」の振り分け
- Streamlit UI での要確認レコードの人手確認・修正
- 確定結果からのルール候補学習(learn)
- 出力アダプタ: 家計簿CSV / Googleスプレッドシート(GAS) / freee取込CSV
- 架空レシートによるデモ(APIキー不要)

### やらないこと (Out)
- 画質を補正する前処理(傾き補正・二値化・ノイズ除去) — VLMに直接読ませる。
  品質不足なら要確認に回り、再撮影すればよい。
  ただし送信できる形に整える処理(回転補正・縮小・JPEG化)は行う(FR-2)
- AIによる費目の推測 — ルールに無い店の費目は人が決め、それがルールに育つループを優先する
- 完全自動運転 — 要確認ゼロ化は目標にしない(原則1に反する)
- クラウドサーバ常駐 — ローカル(Mac)実行のみ。プライバシーとコストの観点

## 3. 機能要件

### FR-1 取り込み
- `data/inbox/` に置かれた画像(jpg / jpeg / png / heic / heif)のうち、未処理分だけを処理する。
  HEIC は事前に変換しなくてよい(FR-2 で自動変換)
- 同一画像の二重処理を防止する(ファイル内容の SHA-256 ハッシュで管理)
- 1枚の抽出に失敗しても(API障害・壊れた画像など)残りの処理を続ける。
  失敗した画像は保存せず理由を表示し、次回の処理で自動的に再挑戦する
- データ置き場は環境変数 `RECEIPTPILOT_DATA` で切り替えられる(既定 `data/`。デモは `data/demo/`)

### FR-2 抽出 (extract)
- Claude API の tool 定義で型を強制した構造化抽出(自由文パースはしない)
- 抽出項目: 店名(印字のまま)、日付(YYYY-MM-DD)、合計、税額、明細(品名/金額)、
  支払方法、読み取り上の注意(かすれ等のメモ)。通貨は読み取らず円(JPY)で固定
- 読めない項目は推測で補完させず null にする(プロンプトで指示)
- 明細には購入した商品の行だけを入れ、小計・税・合計・値引き・ポイント・支払いの行は入れない。
  税額は8%と10%を合算した消費税の合計とする(プロンプトとツール定義で指示)
- 係員・会員の氏名、カード番号・会員番号などの個人情報は、どの項目(メモを含む)にも書かせない
- 送信前に画像を整える: EXIF の向きを補正 → 長辺 1568px 以下に縮小 → JPEG 化
  (iPhone写真は大きく、そのままではサイズ上限で失敗するため)
- モデルは `extract.py` の `DEFAULT_MODEL` で切替(既定: claude-sonnet-4-6 / 低コスト: claude-haiku-4-5)
- 抽出器の選択: 環境変数 `RECEIPTPILOT_EXTRACTOR`(mock / claude)があればそれに従う。
  無ければ APIキーがあれば Claude、なければ MockExtractor
- オフラインテスト用に MockExtractor を同梱(画像と同名の JSON を読む。APIキー不要)
- 検算(明細合計と合計の突合)は抽出ではなく判定(FR-5)で行う

### FR-3 店名正規化(ブランド抽出)
- 店名に**スペース(半角・全角)があるときだけ**、先頭の語をブランド名とし、支店名を落とす
  (例: 「ローソン 駅前店」→「ローソン」)
- スペースが無い場合は記号(「-」など)があっても分割せず、印字のまま保持して人に決めさせる
  (「セブン-イレブン」のように記号が店名の一部であることがあり、自動分割は原理的に曖昧 → 原則1)
- 自分ルールに一致した場合は、ルールに登録したブランド名を使う

### FR-4 自分ルール (rules)
- payee_rules.yaml: 店名パターン → 費目・ブランド名の対応
  - 置き場所: データ置き場に `payee_rules.yaml` があればそれを、無ければ `masters/payee_rules.yaml`
- 照合前に全角/半角・大文字/小文字・ハイフン類(‐ – − など)のゆれを正規化する(NFKC + ハイフン統一。長音「ー」は対象外)
- マッチ方式: 完全一致 > 前方一致 > 部分一致 の優先順(既定は部分一致)
- 費目を決めるのはルールだけ。AIによる費目推測は行わない(原則2。2章 Out 参照)

### FR-5 判定 (judge) — 「ルールが信用を獲得する」
一律しきい値は機能しない(前回実測)。金額×ルール既知性の二軸で判定する。
上から順に調べ、最初に当てはまった行で決まる:

| 順 | 条件 | 判定 |
|---|---|---|
| 1 | 日付・金額・費目のいずれかが無い(ルールに無い店は費目が無い) | 要確認 |
| 2 | 日付が YYYY-MM-DD として不正 / 未来の日付 / 金額が0円以下 | 要確認 |
| 3 | 検算が合わない: 「明細計 = 合計」(内税)でも「明細計 + 税額 = 合計」(外税)でもない。1円単位の完全一致のみ。明細が無ければ検算は省略 | 要確認 |
| 4 | 30,000円超 | 要確認(金額の絶対防衛線) |
| 5 | 自分ルールに載っている店で 20,000円以下 | 自動確定 |
| 6 | 自分ルールに載っている店で 20,000円超 | 要確認 |
| 7 | ルールに無い店で 3,000円以下 | 自動確定 |
| 8 | ルールに無い店で 3,000円超 | 要確認 |

- 判定理由は必ずレコードに記録し、確認画面に表示する(監査可能性)
- 注: 現状は AI が費目を推測しないため、ルールに無い店は 1 で必ず要確認になる。
  7・8 は将来 AI 推測を入れた場合の上限としてコードに残している
- 想定例: よく行く店のルールを1つ足すと、その店の 20,000円以下のレシートは以後自動確定に回る
  (実レシートでの実測は M1 で記録する)

### FR-6 学習 (learn)
- 人手確定した (店名, 費目) を記録する(`data/store/confirmations.jsonl`)
- 学習の店名は、人が確認画面で直したブランド名を優先する(無ければ FR-3 のブランド抽出)
- 同じ対応付けが2回確定され、まだルールに無ければ、ルール候補として提案する(自動追加はしない)
- 採用は人が確認画面で行い、FR-4 のルールファイルに部分一致ルールとして追記する

### FR-7 出力アダプタ
- FR-7.1 共通IF: `validate(record) -> list[str]`(問題の一覧。空なら出力可)と
  `emit(records, out_dir) -> (出力パス, 弾いた理由の一覧)`。
  アダプタ固有の検査は `extra_validate` で追加する
- FR-7.2 **最終検証ゲート(全アダプタ必須)**: 項目充足に加えて
  `status == "confirmed"` を必ず検査する。未確定レコードは全項目が
  埋まっていても書き出さない(前回、status未検査バグで事故りかけた教訓)。
  この検査は基底クラスに固定し、各アダプタから省略できない構造にする
- FR-7.3 CSV の安全対策: Excel で文字化けしないよう BOM 付き UTF-8 で書く。
  店名が `=` `+` `-` `@` などで始まる場合は先頭に `'` を付け、数式として実行されないようにする
- kakeibo_csv: `data/out/kakeibo.csv`(日付/店名/費目/金額)
- gas_sheet: `data/out/gas_payload.json`(GAS Webhook へ POST する JSON。送信は curl 等で手動)。
  受け側の `tools/gas/kakeibo_sheet.gs` は元画像名で二重登録を防ぐ
- freee: `data/out/freee_import.csv`(freee「取引のインポート」形式)
  - 勘定科目は `masters/categories.yaml` の `freee_account` で変換。対応が無い費目は弾く
  - 管理番号は画像ハッシュ。税区分は「課対仕入10%」で固定(軽減税率8%の区別は未対応)
- いずれも日付順に並べる

### FR-8 確認UI (Streamlit)
- 2026-10-20 から、ターミナルを使わない人向けの画面に作り直した。詳細は [UI要件定義.md](UI要件定義.md)
  (取り込み・出力・ルール管理・APIキー設定・お試しモード・終了も画面から行う)
- 取り込み: inbox を処理するボタン。抽出に失敗した画像は理由を表示する
- 統計: 自動確定率(人の手を介さず確定した割合。人手確定は含まない)、
  自動確定・人手確定・要確認の件数
- 要確認一覧: 原本画像 + 判定理由 + 読み取った明細を並べて表示し、
  店名・日付・金額・費目を修正して確定する(先頭の1件は開いた状態で表示)
  - 費目が未定のときは空欄で表示し、選ぶまで確定できない
  - 確定前に入力を検査する(日付の形式・未来日付、金額1円以上、費目の選択)
- 確定時に FR-6 の学習へ記録する
- ルール候補: 提案を表示し、「採用」ボタンでルールに追加する
- 確定済み一覧: 日付・店名・費目・金額・由来(自分ルール / 人手確定)

### FR-9 保存 (store)
- JSONL 追記型ストア(`data/store/records.jsonl`)。DB不要
- 更新も追記で行い、同じ画像ハッシュの最新行を有効とする(履歴が残る = 監査可能)
- 全レコードに status(confirmed / review)と、費目の来歴(rule / human)を持つ。
  status の manual と来歴の extractor は将来用の予約で、現状は使っていない

### FR-10 デモ
- `python3 run.py demo` で、架空レシート(`samples/`)とデモ用ルールから `data/demo/` を作り直し、
  Mock 抽出で処理する。APIキー不要で、判定の各パターンと学習ループを確認できる
- 架空レシートは `tools/make_samples.py` で生成する。実物のレシートは置かない

## 4. 非機能要件

- **プライバシー**: 画像・データはローカル保持。API送信は抽出時の画像のみ。
  `data/` と `private/` は Git 管理外。
  B2B展開時は個人情報保護法対応(利用目的明示・保管期間)を要件化
- **コスト**: 1枚あたり数円程度(sonnet、目安)。月100枚で誤差レベル
- **可搬性**: Python 3.11+(3.11〜3.13 で自動テスト)。
  依存は anthropic / streamlit / pyyaml / pillow / pillow-heif
- **品質**: `pytest` で APIキー無しに全段を検証し、GitHub Actions で push のたびに実行する
- **再開性**: 再開手順は `private/HANDOFF.md`(Git 管理外のローカルメモ)を常に最新化する

## 7. 実物レシートでの検証結果(M1)

2026-10-20、手元の実物レシート4枚(スーパー2・コンビニ1・ガソリンスタンド1。うち3枚が外税)を
claude-sonnet-4-6 で読み取り、人が作った正解データと突き合わせた(`tools/evaluate.py`)。

### 項目別の正解数(4枚)

| 項目 | 修正前 | 修正後 |
|---|---|---|
| 店名 | 4 | 4 |
| 日付 | 4 | 4 |
| 合計金額 | 4 | 4 |
| 税額 | 4 | 3 |
| 明細(件数・金額) | 3 | 4 |
| 支払方法 | 4 | 4 |

### 見つかった問題と対応

| 問題 | 影響 | 対応 |
|---|---|---|
| AIが店名のハイフンを別の文字(‐ U+2010)で返し、「セブン-イレブン」のルールに当たらない | 自動確定できるものが要確認に | ハイフン類を正規化(FR-4) |
| 外税レシートは明細が税抜のため、検算が必ず不一致になる | ルールを登録しても外税は全件要確認に | 「明細計 + 税額 = 合計」も一致とする(FR-5) |
| 小計・税の行まで明細に入れた(1枚) | 検算不一致で要確認(誤確定はなし) | 明細の範囲をプロンプトで指示(FR-2)→ 修正後は4枚とも正確 |
| AIのメモに係員の氏名・カード番号の一部が書かれた | 個人情報の記録 | 書かないようプロンプトで指示(FR-2)→ 修正後は「記録省略」 |

### 判定結果

- 修正後、今のルールのままで自動確定 1枚(セブン-イレブン)。他の3枚は店がルールに無いため要確認
- 3店のルールを足した場合の試算: 自動確定 3枚、要確認 1枚
- 要確認の1枚(トライアル)は、税額を578円と読み違えた(正しくは361円。税の欄が2段ずれて印字されている)。
  検算(明細計3,986 + 税578 ≠ 合計4,347)で検知して要確認に回った
- **誤った自動確定は0件**。読み違いは検算で止まり、原則1(迷ったら安全側)どおりに動いた

### 今後の確認事項

- 残り6枚(感熱紙のかすれ・折れ・1万円以上・値引き行のあるもの)で同じ評価を行う
- 税欄のレイアウトが複雑なレシートで税額を読み違える傾向があるかを見る
